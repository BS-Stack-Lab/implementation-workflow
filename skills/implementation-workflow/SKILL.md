# 문서 기반 구현 워크플로

요청된 구현을 끝까지 수행한다. 작업을 시작하기 전에 [단계와 완료 기준](references/workflow.md)과 [서브에이전트 운영](references/orchestration.md)을 읽고, 현재 저장소의 지침·관련 스킬·실제 명령을 확인한다. 각 단계의 증거를 남기되 형식만 채우기 위한 작업은 만들지 않는다.

## 핵심 경계

- 요청 문서와 실제 변경 범위를 기준으로 작업 영역을 먼저 판별한다. 프론트엔드만 작업하면 `frontend-design.md`만, 백엔드만 작업하면 `backend-design.md`만, 둘 다 작업하면 두 설계 문서를 각각 작성한다. 각 문서에서 요구사항·수용 기준·테스트 시나리오를 연결한다. 두 영역을 모두 작업할 때만 API·데이터 계약과 변경 순서를 교차 확인한다.
- **매 새로운 구현 요청마다** 사용자에게 설계 문서 작성 후 **독립 검토가 끝나면 바로 구현**할지, **설계 문서를 직접 검토한 뒤 구현**할지 두 가지를 반드시 묻는다. 이전 요청·다른 저장소·이전 대화에서 선택한 방식을 재사용하지 않는다. 사용자가 이번 요청의 질문에 명시적으로 답하기 전에는 방식을 추정하거나 기본값으로 선택하지 않는다. 답변 참조와 선택을 `immediate` 또는 `user-review`로 기록한다. 영역을 결정한 뒤 플러그인 루트의 `scripts/orchestrate.py --scope --review-mode`로 작업 그래프를 확인하고 `scripts/workflow_harness.py init --mode-reference`로 저장소 밖 로컬 작업 폴더를 만든다. 설계 게이트 `check --gate design`이 통과해야 구현한다. 테스트·코드 검토·QA 기록을 남긴 뒤 `check --gate final`로 완료 상태를 확인한다. 하네스는 기록의 존재와 순서를 검증하며, 실제 사용자 응답과 테스트 실행을 대신하지 않는다.
- `user-review`를 선택하면 설계 초안을 작성하자마자 해당 문서의 **클릭 가능한 절대 로컬 경로**를 사용자에게 전달해 검토 기회를 제공한다. 사용자의 수정 의견을 반영할 때마다 바뀐 문서를 다시 보여준다. 독립 검토 결과와 최종 설계 문서를 함께 보여주고 사용자가 명시적으로 확인할 때까지 구현하지 않는다. `immediate`를 선택하면 독립 검토가 통과한 설계로 진행하며 별도 설계 확인을 기다리지 않는다.
- 작성한 각 설계 문서를 설계 작성에 참여하지 않은 **서로 다른 서브에이전트 3명**에게 읽기 전용으로 검토시킨다. 두 영역을 모두 작업하면 각 영역과 계약 교차 검토에 각각 3명을 배정한다. 세 결과 중 하나라도 수정을 요구하면 발견 사항을 통합 보고하고 승인받은 뒤 수정된 설계를 3명 모두 다시 검토한다. 실제 서브에이전트 3명을 확보하지 못하면 수동 검토로 완료 처리하지 말고 미완료 사유를 보고한다.
- 설계에 문제가 있어 **설계 문서를 바꿔야 할 때**는 선택한 방식과 관계없이 발견 사항과 수정안을 먼저 사용자에게 보고하고 승인받는다. 승인 전에는 해당 설계 변경이나 그에 의존하는 구현을 진행하지 않는다. `user-review`에서는 수정 후 최종 설계의 사용자 확인도 다시 받는다.
- 구현은 확정된 설계를 따른다. 독립적인 영역만 병렬 위임하고, 공유 파일의 동시 편집은 피한다.
- 구현 후 작업한 영역의 관련 테스트부터 넓은 검사로 진행한다. 구현에 참여하지 않은 서로 다른 읽기 전용 서브에이전트 3명에게 영역별 코드 변경을 검토시킨다. 코드 검토가 통과하면 구현에 참여하지 않은 서로 다른 서브에이전트 3명이 영역별 QA를 수행한다. 두 영역을 모두 작업하면 `frontend-qa.md`와 `backend-qa.md`를 각각 작성하고 연동 QA도 3명이 수행한다. 각자의 원본 결과와 통합 리포트를 로컬에 보관한다. 결함 수정으로 코드 상태가 바뀌면 관련 검사·코드 검토·QA를 현재 코드 기준으로 다시 수행한다.
- 사용자에게 방식 선택, 설계 변경 승인, 최종 설계 확인, 기타 필수 정보를 물을 때는 해당 질문 유형에 사용 가능한 Codex 질문 UI를 우선 사용한다. 간단한 선택지와 자유 입력을 제공하고 답변을 기다린다. UI를 사용할 수 없는 환경에서는 일반 대화로 묻는다. '질문 답하기' 버튼의 정확한 표시는 Codex 클라이언트가 결정하며 스킬이나 훅이 강제로 만들 수 없다.
- `README.md` 외에 생성하는 설계 초안, 검토 기록, QA 기록과 최종 Markdown 리포트는 **`~/Documents/docs/` 아래** 저장소·브랜치별 폴더에 보관한다. 현재 작업 항목이 식별되면 `init --work-item <name>`으로 기존 작업 폴더를 재사용한다. 기존에 사람이 만든 브랜치·작업 폴더가 있으면 연관성을 확인한 뒤 `init --parent-dir <existing-folder>`로 그 안에 새 실행 폴더를 만든다. 여러 후보가 있거나 소속이 불명확하면 질문 UI로 사용자에게 선택을 묻는다. 매번 고유 실행 폴더를 만들어 기존 문서를 덮어쓰지 않는다. `--run-dir`로 새 폴더를 명시할 수도 있다. 모든 경로는 docs 아래이면서 Git 저장소 밖이어야 한다. 기존 `~/.codex/implementation-workflow-runs/` 실행은 후속 명령만 지원한다. 플러그인은 문서를 업로드하지 않지만 `~/Documents`의 운영체제 클라우드 동기화 설정까지 막지는 못한다.
- 기본 정책은 `README.md` 외 문서의 커밋·푸시·병합 금지다. `SKILL.md`도 포함한다. 사용자가 특정 문서의 게시를 직접 요청하면 그 문서에 한정해 승인된 예외로 취급하되, 적용된 GitHub 규칙을 우회할 수 있다고 가정하지 않는다.
- 로컬 검사만으로 GitHub 전체의 푸시·병합 차단을 보장하지 않는다. 저장소 또는 조직의 원격 규칙과 필수 검사를 확인해야 한다.

## 최종 보고

작업별 로컬 폴더에 **실제로 작업한 영역의** 설계·QA 문서만 작성한다. 두 영역을 모두 작업한 경우에만 `integration-qa.md`도 작성한다. `final-report.md`에는 기준 문서, 해당 설계의 결정과 승인 내역, 변경 사항, 실제 실행한 검사와 결과, 해당 영역의 세 코드 검토와 세 QA 결과, 상충 의견과 미해결 항목, 발견·수정한 문제, 남은 위험과 미검증 항목을 요약하고 각 원본·통합 문서의 로컬 경로를 연결한다. 수행하지 않은 검사를 통과로 쓰지 않는다.
