# 문서 기반 구현 워크플로

요청된 구현을 끝까지 수행한다. 작업을 시작하기 전에 [단계와 완료 기준](references/workflow.md)과 [서브에이전트 운영](references/orchestration.md)을 읽고, 현재 저장소의 지침·관련 스킬·실제 명령을 확인한다. 각 단계의 증거를 남기되 형식만 채우기 위한 작업은 만들지 않는다.

## 핵심 경계

- 요청 문서와 실제 변경 범위를 기준으로 작업 영역을 먼저 판별한다. 프론트엔드만 작업하면 `frontend-design.md`만, 백엔드만 작업하면 `backend-design.md`만, 둘 다 작업하면 두 설계 문서를 각각 작성한다. 각 문서에서 요구사항·수용 기준·테스트 시나리오를 연결한다. 두 영역을 모두 작업할 때만 API·데이터 계약과 변경 순서를 교차 확인한다.
- 작업 시작 시 사용자에게 설계 문서 작성 후 **독립 검토가 끝나면 바로 구현**할지, **설계 문서를 직접 검토한 뒤 구현**할지 묻는다. 응답 전에는 방식을 추정해 구현으로 넘어가지 않는다. 선택을 `immediate` 또는 `user-review`로 기록한다. 영역을 결정한 뒤 플러그인 루트의 `scripts/orchestrate.py --scope --review-mode`로 작업 그래프를 확인하고 `scripts/workflow_harness.py init`으로 저장소 밖 로컬 작업 폴더를 만든다. 설계 게이트 `check --gate design`이 통과해야 구현한다. 테스트·코드 검토·QA 기록을 남긴 뒤 `check --gate final`로 완료 상태를 확인한다. 하네스는 기록의 존재와 순서를 검증하며, 실제 사용자 승인과 테스트 실행을 대신하지 않는다.
- `user-review`를 선택하면 설계 초안을 작성하자마자 해당 문서의 **클릭 가능한 절대 로컬 경로**를 사용자에게 전달해 검토 기회를 제공한다. 사용자의 수정 의견을 반영할 때마다 바뀐 문서를 다시 보여준다. 독립 검토 결과와 최종 설계 문서를 함께 보여주고 사용자가 명시적으로 확인할 때까지 구현하지 않는다. `immediate`를 선택하면 독립 검토가 통과한 설계로 진행하며 별도 설계 확인을 기다리지 않는다.
- 작성한 설계 문서만 **독립 서브에이전트**에게 읽기 전용으로 검토시킨다. 두 영역을 모두 작업하면 영역별 검토와 계약 교차 검토를 수행한다. 검토자는 구체적 위치, 영향, 수정안을 보고한다. 서브에이전트를 사용할 수 없으면 그 한계를 밝히고 별도 검토 단계를 수행한다.
- 설계에 문제가 있어 **설계 문서를 바꿔야 할 때**는 선택한 방식과 관계없이 발견 사항과 수정안을 먼저 사용자에게 보고하고 승인받는다. 승인 전에는 해당 설계 변경이나 그에 의존하는 구현을 진행하지 않는다. `user-review`에서는 수정 후 최종 설계의 사용자 확인도 다시 받는다.
- 구현은 확정된 설계를 따른다. 독립적인 영역만 병렬 위임하고, 공유 파일의 동시 편집은 피한다.
- 구현 후 작업한 영역의 관련 테스트부터 넓은 검사로 진행한다. 별도 읽기 전용 서브에이전트에게 작업한 영역의 코드 변경을 검토시키고, 해당 영역의 QA 리포트만 작성한다. 두 영역을 모두 작업하면 `frontend-qa.md`와 `backend-qa.md`를 각각 작성하고 연동 QA도 수행한다. 발견한 구현 결함은 요청 범위 안에서 수정하고 필요한 검사를 다시 한다.
- 설계 초안, 검토 기록, QA 기록, 최종 Markdown 리포트는 **`~/.codex/implementation-workflow-runs/` 아래 작업별 폴더**에 저장한다. 하네스가 대상 Git 저장소 및 다른 Git 저장소 내부 경로를 거부한다. 이 경로를 사용할 수 없으면 작업을 멈추고 사용자에게 로컬 보관 정책 변경을 요청한다. 원격 저장소·클라우드 동기화 폴더로 업로드하지 않는다.
- 기본 정책은 `README.md` 외 문서의 커밋·푸시·병합 금지다. `SKILL.md`도 포함한다. 사용자가 특정 문서의 게시를 직접 요청하면 그 문서에 한정해 승인된 예외로 취급하되, 적용된 GitHub 규칙을 우회할 수 있다고 가정하지 않는다.
- 로컬 검사만으로 GitHub 전체의 푸시·병합 차단을 보장하지 않는다. 저장소 또는 조직의 원격 규칙과 필수 검사를 확인해야 한다.

## 최종 보고

작업별 로컬 폴더에 **실제로 작업한 영역의** 설계·QA 문서만 작성한다. 두 영역을 모두 작업한 경우에만 `integration-qa.md`도 작성한다. `final-report.md`에는 기준 문서, 해당 설계의 결정과 승인 내역, 변경 사항, 실제 실행한 검사와 결과, 해당 영역의 코드 리뷰와 QA 결과, 발견·수정한 문제, 남은 위험과 미검증 항목을 요약하고 각 문서의 로컬 경로를 연결한다. 수행하지 않은 검사를 통과로 쓰지 않는다.
