# 코드 검토·QA·최종 보고 단계

테스트 코드 검토는 자동 테스트 명령 실행 및 QA와 구분한다. 코드 검토자의 `tests-maintainability` 초점은 수용 기준·위험과 테스트 assertion의 연결, 실패를 실제로 잡는 assertion, 외부 동작 중심 검증, 격리·결정성, mock/fixture의 적정성을 확인한다. 신규 v8 run의 지정 슬롯(Full slot 3, Light slot 1)은 JSON `test_code_assessment`를 반드시 출력한다. `outcome`은 `verified|not-needed`, `rationale`은 비어 있지 않은 문자열, `acceptance_criteria`는 전체 수용 기준 ID, `required_test_ids`는 verification plan의 필수 `kind=test` ID 전체, `change_paths`는 현재 영역에서 실제 변경된 경로의 비어 있지 않은 집합이다. `verified`는 고유한 변경 경로를 하나 이상 `reviewed_test_paths`에 넣고 각 경로마다 `{path, location, test_behavior}`를 `test_path_evidence`로 제공한다. 프로젝트가 정한 파일 이름·확장자 규칙을 추정해 강제하지 않는다. 저장소별 테스트 명명 규칙과 인라인 테스트는 정확한 기호·위치와 검증 동작으로 설명한다. `omission_category`는 null이다. `not-needed`는 `reviewed_test_paths: []`, `test_path_evidence: []`와 `omission_category` 중 하나(`documentation-only`, `formatting-only`, `mechanical-rename`, `low-risk-simple-change`)를 사용한다. `low-risk-simple-change`는 영향 범위가 작고 외부 동작·계약·상태·오류·권한·데이터·설정·연동 및 고위험 조건이 바뀌지 않을 때만 허용한다. 생략 근거와 기존/대체 검증은 rationale에 적고 독립 검토자가 타당성을 확인한다. 자동 테스트 명령은 새 테스트 코드 작성 여부와 무관하게 별도로 계속 실행한다. 새 테스트가 필요하다고 판정되면 테스트 코드를 보완하고 영향받는 자동 검사·리뷰·QA를 다시 수행한다. 별도 에이전트는 추가하지 않는다.

1. 구현에 참여하지 않은 읽기 전용 서브에이전트에게 코드 검토를 맡긴다. `light`와 `balanced`는 담당자 1명이 자기 영역의 모든 확인 항목을 검토하고, `full`은 서로 다른 3명이 관점을 나눈다. policy v3에서는 코드 검토자가 `risk_level`도 판정해 결과 JSON과 이벤트에 남긴다. 현재 프로필 범위보다 높은 위험이 나오면 QA로 진행하지 않고 계획을 상속한 새 full 실행으로 올린다. 기존 유지보수성 검토에는 중복 로직, 필요 이상의 추상화·의존성·보일러플레이트, 요청 범위 밖 변경이 있는지도 포함한다. 이 확인은 수용 기준을 구현하는 데 필요한 복잡성이나 보안·검증 조치를 제거하라는 뜻이 아니다. 설계와 다른 단순화가 필요하면 승인 없이 적용하지 않고 기존 설계 변경 절차를 따른다. `review_brief.py`의 짧은 브리프와 시작 커밋 대비 diff·설계·원문 경로를 제공하고 `fork_turns: none`을 우선 사용한다. 구현을 먼저 커밋했다면 v7의 `base_commits` 또는 명시적 `--base <시작-커밋>`으로 커밋된 변경 경로가 브리프에 남는지 확인한다. 공식 출처의 주장과 코드 연결도 해당 역할에 포함한다. 실제 agent ID를 기록한다.
2. v5에서 각 결과의 JSON 원본은 `render_result.py`로 슬롯별 Markdown과 통합 문서를 만든 뒤 `agent-result --stage code-review --result-json --model <actual> --effort <actual> --model-reason <selection-or-fallback> --context-mode <isolated|full-fallback> --context-reason <actual-reason>`에 묶는다. 지정 슬롯의 assessment도 같은 JSON/Markdown 원본 해시에 결합된다. 발견 사항은 해결 근거를 `resolve-agent`에 기록하고 현재 코드에서 선택한 프로필의 검토자 전원이 다시 검토한다.
3. 선택한 코드 검토가 CLEAR이면 다른 서브에이전트가 QA를 실제 수행한다. `light`는 단일 영역 담당자 1명이 정상·경계·권한·회귀·운영을 모두 검증한다. `balanced`는 각 영역 담당자 1명과 통합 담당자 1명이 자신의 모든 계획 사례를 수행한다. `full`은 서로 다른 3명이 슬롯별 계획 사례를 나눈다. `qa-plan.json`의 각 시나리오에 환경·입력·기대/실제·시각·고유 로컬 증거를 남긴다. 실패·미실행은 `resolve-qa-case`와 새 증거로 재수행한다.
4. 양 영역 `balanced`는 양쪽 QA 통과 후 통합 QA 담당자 1명이 전체 통합 사례를 수행한다. `full`은 서로 다른 3명이 연동 QA를 수행한다. 새 영역 QA가 기록되면 연동 QA를 다시 수행한다. 결함 수정으로 코드가 바뀌면 영향받는 영역과 연동의 검사·검토·QA 게이트를 다시 확인한다.
5. QA 원본을 JSON·Markdown·하네스 이벤트에 묶는다. 집계는 선택한 인원의 결과와 상충 의견을 보존한다. 범위 밖 발견은 질문 ID, 경로, 영향, 사용자 답변 또는 pending 상태와 함께 기록하며 승인 전에는 구현하지 않는다. `final-report.md` 초안은 변경 파일·코드 위치, 각 동작 원리, 실행한 검사, 실제 검토·QA 인원, 발견·수정, 공식 출처, 사용량 관측과 미검증 범위를 포함한다. 변경 코드 인용은 `area:path:new:N`으로 표시한다. 삭제 줄은 `area:path:old:N (baseline:<40자리 SHA>)`으로 표시해 저장 기준을 밝힌다. 하네스는 인용 줄이 실제 diff hunk에 있는지 확인한다. v2-v3 실행은 기존 pending 규칙을 유지한다. policy-v4에서는 선택 질문을 미응답 후속 항목으로, 필수 결정 미응답이나 설계 차단은 incomplete 상태로 보고한다. 어느 경우든 질문을 answered/declined로 꾸미지 않고 보고 상태·질문 hash를 현재 증거에 결합한다. 구버전 중단된 게시 journal은 roll-forward 복구 뒤 자동 unanswered 흔적을 다시 pending으로 열고 report-published 이벤트를 무효화하며 이전 문서를 interrupted 사본으로 보존한다. 보고서는 현재 증거에 결합된다. 그 뒤 `check --gate final`과 `status`의 `complete`를 확인한다. 실패하면 `blocker`와 `next_action`에 따라 같은 실행에서 빠진 검증을 수행하고 완료로 표시하지 않는다.

하네스는 파일 해시와 순서를 검증하지만 사용자 응답·에이전트 신원·실제 테스트의 진실성까지 증명하지 못한다. 코디네이터가 증거를 확인한다. 이전 v2~v4 실행은 기존 `workflow.md`·`orchestration.md`의 절차와 명령을 따른다.
