# 구현·검사 단계

새 테스트 코드 작성 여부는 검사 명령 실행과 별도로 위험 기반으로 결정한다. 문서 전용, 서식·공백 전용, 공개 API·데이터 형식에 영향을 주지 않는 기계적 내부 식별자 rename은 `not-needed` 후보이다. 실행 가능한 코드 변경도 영향 범위가 작고, 동작·계약·상태·오류·권한·데이터·설정·외부 연동을 바꾸지 않으며, 보안·결제·개인정보·데이터 손실·동시성 위험이 없고, 기존 검사 또는 직접 검증으로 회귀 위험을 충분히 다룬다고 판단되면 새 테스트 코드 생략을 검토할 수 있다. 영향이 불명확하거나 실패 비용이 크면 테스트 코드를 작성·수정한다. `not-needed`에는 바뀐 동작·위험과 영향이 낮은 이유, 기존 검사 또는 대체 검증, 새 테스트가 추가 가치를 주지 않는 이유를 `rationale`에 기록하고 코드 검토자가 독립 확인한다. 생략 사유는 `documentation-only`, `formatting-only`, `mechanical-rename`, `low-risk-simple-change` 중 하나로 기록한다. 새 테스트 코드 생략은 각 영역에서 계획된 필수 테스트 명령 실행을 생략하지 않는다.

1. `workflow_harness.py status --run-dir <run-dir>`로 현재 단계와 차단 사유를 확인한다. `design` 게이트가 현재 설계·계획에 대해 통과했으면 승인 설계의 범위대로 구현한다. `immediate` 작업은 게이트 통과 후 같은 작업에서 계속한다. 코드를 고르기 전에 요청과 변경 경로의 실제 흐름을 읽어 문제를 이해한다. 범위가 바뀌면 설계로 돌아간다.
2. 적용할 프레임워크·런타임·라이브러리·프로토콜의 실제 버전을 저장소 설정과 공식 문서/API 레퍼런스에서 확인한다. 동작 근거와 적용 파일·함수·버전을 `official-sources.json`에 기록한다. 출처 manifest 변경은 현재 설계 게이트를 무효화하므로 구현 전에 다시 통과시킨다. 공식 근거가 없으면 이유와 대체 검증을 남긴다. 구현 접근은 기존 코드·유틸 재사용, 표준 라이브러리·네이티브 플랫폼 기능, 이미 설치된 의존성, 새 코드·의존성 순으로 검토하고 수용 기준을 만족하는 첫 번째 방법을 선택한다. 새 의존성·추상화·보일러플레이트는 앞선 방법으로 요구사항을 충족하지 못할 때만 추가한다. 코드 줄 수를 줄이려고 수용 기준, 입력 검증, 보안, 오류 처리, 접근성, 데이터 손실 방지 또는 검증을 낮추지 않는다.
3. 새 policy v3의 두 영역 병렬 작업에는 `impact-map.json`의 `exclusive_paths` exact 경로와 이유를 영역별로 선언한다. 기존 frontend/backend/shared glob은 영향 digest 계산에만 사용하며 소유권 증거로 사용하지 않는다. `shared/`, `contracts/`, `schema/`, `schemas/` 경로, 루트 설정·lockfile, 배포·보안 파일은 항상 공유다. 현재 그래프에는 통합 코드 리뷰 단계가 없으므로 양 영역 설계에 shared 경로가 필요하면 해당 저장소를 소유 단일 영역으로 지정한 별도 `full` run에서 shared 변경·검토·QA를 완료한다. 검토된 소스 계약은 다음 run의 `HEAD` 기준선에 포함되도록 로컬 커밋한 뒤 FE/BE run을 시작하며, 이 커밋은 push하지 않는다. 이후 FE/BE run은 shared 파일을 건드리지 않는다. 동일 Git checkout은 소유 경로와 무관하게 구현·검토를 직렬화하고 frontend 코드 검토가 backend 구현보다 먼저 끝나야 한다. 별도 checkout만 exact 경로가 단일 영역에 귀속된 경우 병렬화할 수 있다. 구현 뒤 `git status --porcelain=v2 -z`와 diff에서 tracked·untracked·삭제·rename 양끝 경로를 모아 계획과 대조한다. 누락·겹침·공유·예상 밖 경로는 통합 전에 직렬 재검증한다. 기존 v2 glob 의미는 유지한다.
4. `verification-plan.json`의 필수 명령을 각 영역의 지정된 저장소에서 실제로 실행한다. `python3 <plugin-root>/scripts/run_check.py --run-dir <run-dir> --repo <area-repo> --area <area> --command '<planned-command>'`는 해당 체크아웃·영역·코드 해시·로그·종료 코드를 manifest에 남긴다. 연동 검사는 지정된 연동 저장소에서 실행하고 FE·BE·연동 저장소의 코드 상태를 함께 확인한다. 연결 작업 트리의 git-dir가 바뀌면 이전 증거를 재사용하지 않는다. 단일 영역에서는 `--area`를 생략할 수 있다. `evidence_summary.py --run-dir <run-dir> --manifest-file <path>`는 짧은 전달용 요약일 뿐 판정을 바꾸지 못한다.
5. `check-record --area <area> --name <planned-id> --status <pass|fail> --manifest-file <path>`는 manifest의 계획 명령·종료 코드·로그 해시와 일치해야 한다. 실패·미실행 뒤에는 `resolve-check`에 원인·조치를 남기고 **새 실행 시도**로 재검사한다. 환경 복구나 설명만으로 PASS로 기록하지 않는다. 선택 검사의 미실행은 `--status not-run --reason --unverified`로 기록한다.
6. 변경한 영역의 필수 검사가 모두 PASS여야 코드 검토를 시작한다. 검토 후 코드가 바뀌면 현재 코드 기준으로 관련 검사·선택한 1인/3인 코드 검토·QA를 다시 수행한다. light에서 위험 경로가 추가되면 full 실행으로 다시 시작한다. 테스트는 실제 변경 위험을 확인하는 수준으로 둔다. 단계가 중단되면 같은 실행 폴더의 `status`를 조회해 `next_action`부터 계속한다.

모든 로그·manifest·요약은 로컬 실행 폴더에 보관한다. `README.md` 외 생성 문서를 Git에 커밋·푸시·병합하지 않는다.
