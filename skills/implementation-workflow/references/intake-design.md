# 요청·설계·승인 단계

1. 원문 요청의 경로·버전, 프론트엔드·백엔드 각각의 저장소 루트·브랜치·사용자 변경, 실제 코드·검사 명령을 확인한다. 같은 저장소라면 두 영역에 같은 루트를 지정할 수 있다. 작업 영역만 설계한다. 프론트엔드면 `frontend-design.md`, 백엔드면 `backend-design.md`, 둘 다면 두 문서와 API·데이터 계약을 각각 작성한다.
2. 작업 ID에 해당하는 `~/Documents/docs/` 실행 폴더를 먼저 찾는다. v8 미완료 실행이면 `scope-register.json`의 pending 질문부터 복원하고, 그 뒤 `workflow_harness.py status --run-dir <run-dir>`로 저장된 모드·범위·`next_action`을 확인한다. v2-v7은 기존 status 재개 절차를 따른다. 다른 저장소, 다른 작업 ID, 완료된 실행이나 모호한 후보를 임의로 이어 붙이지 않는다.
3. **새 구현 요청일 때만** 질문 UI로 독립 검토 후 바로 구현(`immediate`)과 사용자가 설계를 검토한 뒤 구현(`user-review`) 중 하나를 명시적으로 선택받는다. 이 요청의 응답을 `--mode-reference`에 남긴다. 이전 작업의 선택을 재사용하지 않는다. `--work-item`으로 동일 작업의 미완료 실행을 재사용하며, 명시적 새 실행에는 `--new-run`을 사용한다. 생성 문서는 관련 Git 저장소 모두의 밖에 둔다.
4. 위험을 `low|medium|high|unknown`으로 분류한다. low 단일 영역은 `light`, low/medium 두 영역은 `balanced`, 그 외는 `full`이다. low/medium에서도 `full`을 선택할 수 있다. `python3 <plugin-root>/scripts/orchestrate.py --scope <frontend|backend|both> --review-mode <immediate|user-review> --review-depth <light|balanced|full>`로 계획을 보고 `workflow_harness.py init`에 동일한 `--review-depth`, `--risk-level`, `--risk-reason`을 전달한다. 두 영역은 `--frontend-repo`·`--backend-repo`를 각각 지정하고 필요하면 `--integration-repo`를 지정한다. 기존 실행에서는 `orchestrate.py --run-dir <run-dir>`로 상태와 그래프를 함께 읽는다. 이전 state version의 의미를 새 policy로 다시 해석하지 않는다.
5. 저장소 설정에서 기술·의존성의 실제 버전을 확인하고 그 버전에 맞는 공급자 공식 문서/API 레퍼런스를 조사한다. `official-sources.json`에 출처 ID·게시자·제목·HTTPS URL·문서 버전·확인일·감지한 의존성 버전·버전을 확인한 저장소 근거·기술 주장·적용 파일/함수를 넣는다. 하네스는 필드와 URL을 검사하고, 코디네이터와 검토자는 실제 버전 일치를 원문과 설정에서 대조한다. 적용 가능한 공식 자료가 없으면 `not_applicable`와 이유·대체 검증을 기록한다. 자료를 확인하지 않은 채 추정으로 구현하지 않는다.
6. 설계의 `## 수용 기준`에서 R1/AC-1 같은 고유 ID를 한 줄씩 선언한다. 각 주요 구현 선택은 실제 변경 경로를 이해한 뒤 기존 코드 재사용, 표준 라이브러리·플랫폼 기능, 이미 설치된 의존성, 새 코드·의존성 순으로 검토한다. 설계에는 선택한 접근과 중요한 근거만 적고 대안을 빠짐없이 나열하지 않는다. 새 의존성이나 추상화를 제안할 때는 앞선 선택지로 수용 기준을 충족하지 못하는 이유를 기록한다. 실제 저장소 명령으로 `verification-plan.json`을, 구체적인 입력·절차·기대 결과로 `qa-plan.json`을 작성한다. QA는 `normal`, `boundary`, `authorization`, `regression`, `operations`를 포함하고 모든 기준을 연결한다. light/balanced는 실행 slot 1이며 balanced 계획은 각 시나리오에 full용 `slot`과 balanced용 `balanced_slot: 1`을 함께 둔다. full은 slot 1·2·3을 사용한다. 두 영역이면 연동 시나리오에 `source_area`를 지정한다. 설계·검사 계획·QA 계획·공식 출처를 확정한 뒤 설계 검토를 시작한다.
7. 새 테스트 코드 작성 여부를 검증 명령 계획과 별도로 위험 기반으로 정한다. 문서·서식·기계적 rename 외에도 작고 영향이 제한된 코드 변경이며 계약·상태·오류·권한·데이터·설정·연동 또는 고위험 조건이 바뀌지 않고 기존/대체 검증이 충분하면 `low-risk-simple-change`로 새 테스트 코드를 생략할 수 있다. 영향이나 실패 비용이 불명확하면 테스트 코드를 추가·수정한다. 생략 근거에는 변경 경로, 저위험 판단, 기존/대체 검증 및 새 테스트가 추가 가치를 주지 않는 이유를 포함하고 독립 코드 검토자가 확인한다. 필수 테스트 명령은 항상 계획하고 실행한다.
8. 설계 검토자는 테스트 코드 생략이 허용 범위에 드는지, 위험 경로가 빠지지 않았는지 검토한다. 코드 검토자는 테스트 코드의 기준 연결, assertion 효과, 외부 동작 검증, 결정성·격리성을 검토하고, `not-needed`이면 생략 근거와 대체 증거를 확인한다. 자동 검사 및 QA와 구분해 결과를 남기되 기본 검토 인원을 늘리지 않는다.
9. 질문 UI를 호출해 선택을 요청하면 도구 결과로 질문 전달을 확인한다. 전달 실패·시간 초과·불확실한 결과는 성공으로 처리하지 않고 재시도하거나 대화 질문으로 전환한다. 직접 답하거나 거절한 명시적 응답만 답변으로 인정한다. 무관한 입력이나 모호한 답은 pending을 유지한다.
10. 모든 질문은 유효한 응답 또는 거절을 받을 때까지 같은 ID·revision으로 pending을 유지한다. 질문에 종속되지 않은 구현·검사·리뷰·QA는 계속하고 보고서 초안까지 준비한다. 필수 게이트가 끝나 report 단계에 도달하면 질문 UI를 띄우고, 호스트가 현재 turn을 활성 상태로 유지하는 동안 최대 60초 간격으로 응답을 기다린다. 대기 반복만으로 turn 종료나 앱 종료 후 UI가 살아 있다고 보장할 수 없다. 중단되거나 재개되면 `scope-register.json`에서 pending을 확인하고 같은 ID·revision으로 UI를 다시 표시한다. pending 질문이 있으면 `report-publish`·최종 게이트·assistant final을 보류한다. 재개할 때 `status`보다 pending을 먼저 확인한다. 표준 선택지는 `scope_extension`에 `승인하여 요청 범위에 포함`·`거절하고 요청 범위 유지`, `required_decision`에 `승인`·`거절`을 사용한다. 사용자 지정 선택지는 질문 본문에 정확한 라벨과 의미를 저장한다. pending 질문에서 `report-publish`는 상태와 파일을 바꾸지 않고 실패한다. 구버전 중단 게시 복구는 현재 발행에 붙은 자동 unanswered만 되돌리고 이전 보고서를 interrupted 파일로 보존한다.
11. `user-review`면 설계 초안의 클릭 가능한 절대 경로를 즉시 보여주고 `present`로 기록한다.
12. 설계 작성에 참여하지 않은 읽기 전용 서브에이전트가 프로필별로 독립 검토한다(light/balanced 1명, full 3명). `review_brief.py`로 원문 경로·버전, 적용 공식 출처, 계획·수용 기준·변경 경로를 담은 짧은 브리프를 만든다. 역할은 요구사항 누락, 구조·호환성, 오류·보안·검증 가능성으로 나누고 가능한 한 병렬 실행한다. 한 차례 초기 검토를 목표로 하며, 불필요한 반복은 줄이되 검토 미완료·시간 초과를 PASS로 바꾸지 않는다. `fork_turns: none`을 우선 사용한다. 지원하지 않으면 전체 문맥 전환 이유를 기록한다. 실제 agent ID와 슬롯 초점을 기록한다.
13. 구조화 JSON을 `render_result.py`로 슬롯별 Markdown과 통합 문서로 렌더하고 `review --result-json`에 연결한다. 실제 모델·문맥 선택과 이유를 기록한다. 한 명이라도 필수 수정을 요구하면 선택된 모든 결과를 보고하고 질문 UI로 승인받은 뒤 `approve`를 기록한다. 범위 밖 선택 제안은 `scope_extension`으로 질문하되 원래 작업의 독립 단계를 계속한다. 명시적 거절은 거절로 기록하고 해당 변경은 코드 범위에 추가하지 않는다. 응답이 없으면 같은 질문을 pending으로 유지하고 보고 게시와 final을 보류한다. 승인 전 설계 변경·구현을 하지 않는다. 수정 후 선택한 인원 모두 변경된 기준을 재검토한다.
14. `user-review`면 최종 설계와 검토 링크를 보여주고 사용자 확인을 `accept-design`에 기록한다. `immediate`면 독립 검토가 모두 통과한 뒤 바로 진행한다. `check --gate design` 통과 전에는 구현하지 않는다. 게이트 통과 후 `status`에서 다음 단계를 확인하고, 구현까지 요청된 `immediate` 작업은 구현·검사·코드 검토·QA·최종 보고까지 이어간다. 설계만 요청되었다면 설계 전달에서 마친다.

하네스 명령의 전체 인수는 `python3 <plugin-root>/scripts/workflow_harness.py --help`와 해당 하위 명령 `--help`로 확인한다. v2~v4 실행은 기존 `workflow.md`·`orchestration.md`의 명령을 계속 사용한다.
