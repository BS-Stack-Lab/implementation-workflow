# 단계와 완료 기준

## 1. 요청 해석

1. 요청 문서의 경로·버전·범위를 확인한다.
2. 저장소 루트, 현재 브랜치, 사용자 변경 사항과 프로젝트 지침을 확인한다.
3. 관련 코드·설정·테스트 및 실제 빌드 명령을 찾는다.
4. 문서 사이의 충돌·누락·모호한 요구사항을 기록한다.
5. 기능 요구사항을 관찰 가능한 수용 기준으로 바꾼다.
6. 요청과 실제 변경 범위를 프론트엔드, 백엔드, 두 영역 모두 중 하나로 판별한다. 관련 없는 영역의 설계·검토·테스트·QA 문서는 만들지 않는다.
7. 매 새로운 구현 요청마다 사용자에게 설계 문서 작성 후 독립 검토가 끝나면 바로 구현할지, 직접 설계를 검토한 뒤 구현할지 반드시 묻는다. 이전 요청의 선택을 재사용하지 않는다. 이번 요청에 대한 명시적 답변을 받기 전에는 구현 방식을 추정하지 않는다.
8. 선택한 범위와 검토 방식의 오케스트라 작업 그래프를 출력하고 하네스를 초기화해 대상 저장소 밖 로컬 작업 폴더를 만든다.

완료 기준: 구현 범위, 각 수용 기준의 출처와 사용자가 선택한 검토 방식을 설명할 수 있다.

## 2. 영역별 설계 초안

1. 프론트엔드가 관련되면 `frontend-design.md`에 화면과 사용자 흐름, 상태·입력 검증·오류 표시, 접근성, API 사용, 변경 파일과 테스트 시나리오를 적는다.
2. 백엔드가 관련되면 `backend-design.md`에 API 계약, 도메인 규칙, 데이터·영속성·마이그레이션, 인증·권한, 오류 처리, 변경 파일과 테스트 시나리오를 적는다.
3. 각 문서에 요구사항 ID, 수용 기준, 정상·경계·실패 시나리오, 중요한 선택의 이유와 대안, 구현 순서와 검증 방법을 연결한다. 해당하지 않는 항목은 억지로 채우지 않는다.
4. 양쪽이 관련되면 요청·응답 필드, 상태 코드, 오류 형식, 인증 방식, 데이터 형식, 버전·호환성, 배포·의존 순서가 두 설계에서 일치하는지 대조한다. 계약의 기준은 두 문서에 같은 버전·결정으로 명시한다.
5. 단일 영역 작업은 해당 설계 문서만 만든다.
6. `user-review`를 선택했다면 작성 직후 각 설계 문서의 클릭 가능한 절대 로컬 경로를 전달한다. 프론트엔드와 백엔드를 모두 작업했다면 두 문서 모두 제공한다. 사용자가 수정 의견을 주면 반영하고 변경된 문서를 다시 보여준다.

완료 기준: 작업하는 각 영역의 초안에 수용 기준과 검증 방법이 있고, 두 영역을 모두 작업한다면 영역 간 계약이 서로 맞는다.

## 3. 독립 설계 검토와 사용자 승인

1. 프론트엔드와 백엔드가 모두 관련되면 각 설계를 다른 읽기 전용 서브에이전트에게 맡긴다. 각자 요구 문서·해당 설계 초안·관련 코드의 최소 범위를 읽는다.
2. 영역별 누락, 모순, 호환성, 예외 처리, 테스트 가능성을 검토하고, 두 문서의 API·데이터 계약도 교차 검토한다.
3. 발견 사항은 위치·증거·영향·수정안으로 정리한다.
4. 설계 변경이 필요한 발견 사항은 선택한 방식과 관계없이 사용자에게 보고하고 수정을 승인받을 때까지 기다린다.
5. 승인된 수정안만 해당 영역 설계에 반영한 뒤 변경된 설계와 계약을 다시 확인한다. 승인되지 않은 제안은 미해결 항목으로 둔다.
6. 영역별 검토 문서를 저장하고 하네스에 결과를 기록한다. 변경이 필요하면 실제 사용자 승인 참조를 기록한 뒤 수정·재검토한다.
7. `user-review`라면 독립 검토 결과와 최종 설계 문서의 로컬 링크를 사용자에게 보여준다. 사용자가 명시적으로 설계를 확인하거나 구현 진행을 승인하면 그 응답을 하네스에 기록한다. 수정 의견이 있으면 반영·재공유·재검토한 다음 다시 확인받는다. 응답이 오기 전에는 구현하지 않는다. `immediate`라면 별도 확인 없이 다음 단계로 진행한다.
8. `design` 게이트를 통과시킨다.

완료 기준: 구현에 사용할 해당 영역 설계의 버전과 필요한 승인 상태가 명확하다. `user-review`라면 현재 버전에 대한 사용자 확인도 있다. 두 영역을 모두 작업한다면 공통 계약도 명확하다.

## 4. 구현

1. 확정 설계와 현재 코드의 차이를 다시 확인한다.
2. 해당 영역의 의존 순서에 맞춰 변경 단위를 구현한다. 두 영역을 모두 작업하면 계약을 기준으로 순서를 정하고 독립적인 파일만 병렬 위임한다.
3. 실제 변경 위험을 검증하는 테스트를 함께 추가·수정한다.
4. 각 단위의 관련 검사를 실행하고 실패를 수정한다.
5. 설계 범위를 넘는 변경이 필요하면 해당 부분을 멈추고 설계 검토로 돌아간다.

완료 기준: 요구사항과 수용 기준을 코드 변경에 추적할 수 있다.

## 5. 자동 검증

1. 실제 작업한 영역의 변경 코드에 대한 관련 테스트를 실행한다.
2. 양쪽이 관련되면 API 계약과 사용자 흐름의 연동 테스트를 실행한다.
3. 각 영역에서 저장소가 제공하는 포맷·린트·정적 분석·빌드 중 관련 검사를 실행한다.
4. 실패 원인을 수정하고 해당 검사를 재실행한다.
5. 실행 불가능한 검사는 이유와 미검증 범위를 기록한다.
6. 실행한 검사마다 영역·명령·상태·증거를 하네스에 기록한다. 재검증한 실패는 같은 검사 이름으로 새 결과를 남긴다.

완료 기준: 실행한 검사의 명령·결과·재검사 기록이 있다.

## 6. 독립 코드 검토와 QA

1. 영역별 읽기 전용 서브에이전트에게 해당 diff와 설계·수용 기준을 전달한다.
2. 작업한 영역의 결함, 회귀 위험, 설계 불일치, 테스트 빈틈을 검토한다.
3. 프론트엔드를 작업했으면 `frontend-qa.md`에 화면·상태·입력·오류·접근성의 실제 수행 결과를 기록한다. 백엔드를 작업했으면 `backend-qa.md`에 API·도메인·데이터·권한·오류의 실제 수행 결과를 기록한다.
4. 양쪽이 관련되면 `integration-qa.md`에 API 계약과 프론트엔드·백엔드 연결 흐름의 수행 결과를 기록한다.
5. 각 시나리오에 실행 환경·입력·기대 결과·실제 결과·통과/실패/미검증·증거를 남긴다. 실패는 재현 절차·영향도·조치·재검증 결과를 기록한다.
6. 발견한 구현 문제를 재현·수정·재검증하고 남은 문제의 영향과 미검증 범위를 판정한다.

완료 기준: 관련 영역마다 별도 QA 리포트가 있고, 연동 결과와 코드 검토 발견 사항의 처리 상태가 명확하다.

## 7. Markdown 리포트

`final-report.md`에 기준 문서와 범위, 실제 작업한 영역의 승인된 설계 결정, 변경 사항, 테스트 명령과 결과, 코드 검토 및 QA 요약, 해당하는 경우의 연동 QA 결과, 발견 문제와 조치, 남은 위험, 수용 기준별 통과·실패·미검증 상태를 기록한다. 작성한 설계와 QA 리포트의 로컬 경로를 연결한다. 모든 문서를 대상 Git 저장소 밖의 작업별 로컬 폴더에 저장한 뒤 링크를 제공한다.

보고 전에 하네스의 `final` 게이트를 실행한다. 실패하면 빠진 증거를 실제 수행 결과로 채우거나 미검증 사유를 명시한다.
