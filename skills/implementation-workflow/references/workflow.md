# 단계와 완료 기준

## 1. 요청 해석

1. 요청 문서의 경로·버전·범위를 확인한다.
2. 저장소 루트, 현재 브랜치, 사용자 변경 사항과 프로젝트 지침을 확인한다.
3. 관련 코드·설정·테스트 및 실제 빌드 명령을 찾는다.
4. 문서 사이의 충돌·누락·모호한 요구사항을 기록한다.
5. 기능 요구사항을 관찰 가능한 수용 기준으로 바꾼다. 각 적용 기준에 `R1`, `AC-1` 같은 안정적인 고유 ID를 부여하고 해당 설계의 `## 수용 기준` 절에 한 줄씩 선언한다.
6. 요청과 실제 변경 범위를 프론트엔드, 백엔드, 두 영역 모두 중 하나로 판별한다. 관련 없는 영역의 설계·검토·테스트·QA 문서는 만들지 않는다.
7. 매 새로운 구현 요청마다 사용자에게 설계 문서 작성 후 독립 검토가 끝나면 바로 구현할지, 직접 설계를 검토한 뒤 구현할지 반드시 묻는다. 사용할 수 있는 질문 UI에서 선택지와 자유 입력을 제공한다. 이전 요청의 선택을 재사용하지 않으며 이번 요청에 대한 명시적 답변 전에는 구현 방식을 추정하지 않는다.
8. `~/Documents/docs/`에서 현재 저장소·브랜치·작업에 쓰는 기존 폴더를 확인한다. 자동 생성된 동일 작업 폴더는 `--work-item`으로 재사용한다. 사람이 만든 기존 폴더가 현재 작업의 것임을 확인했다면 `--parent-dir`로 지정하고, 후보가 모호하면 질문 UI로 선택을 묻는다. 선택한 범위와 검토 방식의 오케스트라 작업 그래프를 출력하고 하네스를 초기화해 해당 폴더 아래 새 실행 폴더를 만든다.
9. 요청 범위 밖의 개선은 `scope_extension`, 원 요청에 답이 꼭 필요한 결정은 `required_decision`으로 질문·기록한다. policy-v4에서 선택 질문은 미응답이어도 핵심 작업과 보고서 게시를 막지 않고 후속 작업 표에 남긴다. 필수 결정은 `dependent_paths`와 작업 경로가 겹치는 작업만 차단한다. 그 밖의 단계는 계속한다. 필수 질문이 남았고 현재 turn이 활성 상태라면 답변을 기다리며 종료하거나 incomplete 리포트를 게시하지 않는다. 실제 turn 중단 시 미완료 상태와 pending을 보존하고 재개 시 같은 질문을 재표시한다. `complete=false`, `next_action=answer-question`은 실제로 중단되어 작업을 다음 turn으로 넘길 때 사용한다. 저장 상태의 schema 호환성은 유지하며 버전별 게이트 규칙을 소급 변경하지 않는다. 재개하면 모호한 답으로 pending을 해제하지 않는다.
10. 신규 policy-v4 실행은 `scope-contract.json`에 원 요청·포함 경로·제외 범위·완료 기준·coordinator owner를 저장하고 계획·리뷰·최종 증거에 hash를 결합한다. coordinator 한 명이 전체 그래프와 상태를 소유한다. 서브에이전트는 배정된 영역과 경로만 다루고 범위 변경은 제안으로 반환한다.
11. 설계 검토 상한은 초기 검토 1회와 승인된 수정 후 재검토 1회다. 재검토에 blocking finding이 남으면 `design-blocked` incomplete 리포트를 게시하고 새 실행을 안내한다. 세 번째 설계 digest는 거부한다.
12. 작업 크기·위험으로 프로필을 선택한다: small+low 단일 영역은 light, medium 단일 영역 또는 변경 경로가 분리된 low/medium 양 영역은 balanced, large·high·unknown·고영향 변경은 full이다. 대형 양 영역 변경과 공유 계약/통합 작업은 full이다. light는 단계별 1명과 normal/regression 최소 QA, balanced는 영역별 1명 및 필요한 통합 검증, full은 역할별 서로 다른 3명을 쓴다. 어떤 프로필에서도 설계·필수 검사·코드 검토·QA·리포트 게이트를 생략하지 않는다.
13. 위험을 `low|medium|high|unknown`으로 평가한다. 위험을 정하지 않은 신규 실행은 `unknown/full`이다. task-size 기준과 앞선 프로필 규칙을 함께 적용한다. 코디네이터·설계 검토자·코드 검토자의 위험 판단 중 가장 높은 것을 적용하고, 현재 프로필 범위를 넘으면 필수 계획을 상속한 새 full 실행을 만든다. 짧은 브리프와 병렬 wave 실행으로 대기 시간을 줄이되 timeout이나 검토 미완료를 PASS로 취급하지 않는다.
14. 사용 중인 기술 버전의 공식 공급자 문서/API 레퍼런스를 확인하고 `official-sources.json`에 근거와 적용 코드 경로를 남긴다. 적용 가능한 출처가 검토되지 않았다면 구현 단계로 넘어가지 않는다.

완료 기준: 구현 범위, 각 수용 기준과 공식 근거, 사용자가 선택한 검토 방식, 질문할 범위 밖 항목을 추적할 수 있다.

## 2. 영역별 설계 초안

1. 프론트엔드가 관련되면 `frontend-design.md`에 화면과 사용자 흐름, 상태·입력 검증·오류 표시, 접근성, API 사용, 변경 파일과 테스트 시나리오를 적는다.
2. 백엔드가 관련되면 `backend-design.md`에 API 계약, 도메인 규칙, 데이터·영속성·마이그레이션, 인증·권한, 오류 처리, 변경 파일과 테스트 시나리오를 적는다.
3. 각 문서에 요구사항 ID, 수용 기준 ID, 정상·경계·실패 시나리오, 중요한 선택의 이유와 대안, 구현 순서와 검증 방법을 연결한다. 해당하지 않는 항목은 억지로 채우지 않는다. 하네스가 `## 수용 기준` 절에서 ID를 추출하므로 기준을 누락하거나 같은 ID를 중복하지 않는다.
4. 양쪽이 관련되면 요청·응답 필드, 상태 코드, 오류 형식, 인증 방식, 데이터 형식, 버전·호환성, 배포·의존 순서가 두 설계에서 일치하는지 대조한다. 계약의 기준은 두 문서에 같은 버전·결정으로 명시한다.
5. 단일 영역 작업은 해당 설계 문서만 만든다.
6. `user-review`를 선택했다면 작성 직후 각 설계 문서의 클릭 가능한 절대 로컬 경로를 전달한다. 프론트엔드와 백엔드를 모두 작업했다면 두 문서 모두 제공한다. 사용자가 수정 의견을 주면 반영하고 변경된 문서를 다시 보여준다.

완료 기준: 작업하는 각 영역의 초안에 수용 기준과 검증 방법이 있고, 두 영역을 모두 작업한다면 영역 간 계약이 서로 맞는다.

## 3. 독립 설계 검토와 사용자 승인

1. 실제 저장소에서 발견한 검사로 로컬 `verification-plan.json`을 작성한다. 각 작업 영역에 필수 `test` 검사를 적어도 하나 넣고, 선택 검사는 사유를 남긴다. `qa-plan.json`은 각 영역·슬롯의 시나리오에 고유 ID·수용 기준 ID·절차·기대 결과를 담는다. 설계의 모든 적용 기준이 해당 영역의 시나리오에 연결됐는지 원문 요구사항과 대조한다. 두 영역의 연동 QA는 두 설계의 기준을 참조할 수 있다. 이 계획을 작성한 뒤 각 검토 결과를 하네스에 기록한다.
2. 해당 영역의 설계를 작성에 참여하지 않은 읽기 전용 서브에이전트에게 맡긴다. light/balanced는 한 명이 전체 기준을 보고 full은 서로 다른 세 명이 맡는다. 양 영역의 계약 검토도 balanced는 한 명, full은 세 명이다. 각자 요구 문서·해당 설계 초안·관련 코드의 최소 범위를 읽는다. 오케스트레이터가 출력한 슬롯별 `focus`와 질문을 각각 전달한다.
3. 첫째는 원문 요구사항·수용 기준 누락, 둘째는 구조·호환성, 셋째는 오류·보안·검증 가능성을 중점 검토한다. 두 문서의 API·데이터 계약도 별도 관점으로 교차 검토한다. 관점이 겹친 발견도 원본에서 삭제하지 않고 통합 문서에서 중복을 병합한다.
4. 선택된 각 검토자는 위치·증거·영향·수정안을 별도 원본 문서에 기록한다. 코디네이터는 모든 결론과 상충 의견을 영역별 통합 문서에 정리한다.
5. 한 명이라도 설계 변경을 요구하면 선택된 모든 결과를 수집해 사용자에게 보고하고 수정을 승인받을 때까지 기다린다. 지원되는 질문 UI가 있으면 승인 질문에도 사용한다.
6. 승인된 수정안만 해당 영역 설계에 반영한 뒤 변경된 설계와 계약을 선택 프로필의 모든 검토자가 다시 검토한다. 승인되지 않은 제안은 미해결 항목으로 둔다.
7. 각 검토자의 실제 서브에이전트 ID와 원본 문서를 하네스에 기록한다. 프로필에 필요한 인원을 확보하지 못하면 단계를 미완료로 보고한다.
8. `user-review`라면 독립 검토 결과와 최종 설계 문서의 로컬 링크를 사용자에게 보여준다. 사용자가 명시적으로 설계를 확인하거나 구현 진행을 승인하면 그 응답을 하네스에 기록한다. 수정 의견이 있으면 반영·재공유·재검토한 다음 다시 확인받는다. 응답이 오기 전에는 구현하지 않는다. `immediate`라면 별도 확인 없이 다음 단계로 진행한다.
9. `design` 게이트를 통과시킨다. 이때 설계와 두 계획의 해시가 묶인다. 어느 하나라도 바뀌면 승인·재검토 규칙을 다시 적용하고 게이트를 재실행한다.

완료 기준: 현재 설계 버전에 선택한 수의 독립 검토 결과와 필요한 승인 상태가 있다. `user-review`라면 현재 버전에 대한 사용자 확인도 있다. 두 영역을 모두 작업한다면 공통 계약도 명확하다. 검사·QA 계획과 공식 출처가 실제 코드와 모든 선언된 수용 기준을 덮고 설계 게이트가 통과한다.

## 4. 구현

1. 확정 설계와 현재 코드의 차이를 다시 확인한다.
2. 해당 영역의 의존 순서에 맞춰 변경 단위를 구현한다. 두 영역을 모두 작업하면 계약을 기준으로 순서를 정하고 독립적인 파일만 병렬 위임한다.
3. 새 테스트 코드는 외부 동작 변화와 실패 위험으로 결정한다. 작고 영향 범위가 제한된 코드 변경은 계약·상태·오류·권한·데이터·설정·외부 연동 변화나 보안·금전·개인정보·데이터 손실·동시성 위험이 없고 기존/대체 검증이 충분한 경우 `low-risk-simple-change`로 새 테스트 코드를 생략할 수 있다. 위험 또는 회귀 가능성이 불명확하면 테스트 코드를 추가·수정한다. 생략 사유와 근거는 구현 및 테스트 코드 검토 결과에 남긴다. 테스트 코드 작성 여부와 무관하게 영역별 필수 테스트 명령은 실행한다.
4. 각 단위의 관련 검사를 실행하고 실패를 수정한다.
5. 설계 범위를 넘는 변경이 필요하면 해당 부분을 멈추고 설계 검토로 돌아간다.

완료 기준: 요구사항과 수용 기준을 코드 변경에 추적할 수 있다.

## 5. 자동 검증

1. 실제 작업한 영역의 변경 코드에 대한 관련 테스트를 실행한다.
2. 양쪽이 관련되면 API 계약과 사용자 흐름의 연동 테스트를 실행한다.
3. 각 영역에서 저장소가 제공하는 포맷·린트·정적 분석·빌드 중 관련 검사를 실행한다.
4. 실패 원인을 수정하고 해당 검사를 재실행한다.
5. 실행 불가능한 검사는 이유와 미검증 범위를 기록한다.
6. v4 이하의 기존 실행은 당시 증거 규칙을 따른다. 신규 v8 실행은 `run_check.py`의 manifest로 실제 명령·종료 코드·로그를 검증해 계획된 검사 ID마다 기록한다. 필수 검사는 모두 PASS여야 코드 검토 결과를 기록할 수 있다. 선택 검사를 실행하지 못하면 이유와 미검증 범위를 남긴다. 실패 또는 필수 미실행 뒤에는 `resolve-check`에 원인·조치 근거를 기록하고 같은 ID를 실제 재실행해 새 증거를 남긴다. 환경 복구나 설명만으로 PASS를 기록하지 않는다.

완료 기준: 계획된 필수 검사 전체가 현재 코드와 설계에 대해 PASS이며, 각 시도의 명령·결과·재검사 기록과 변경되지 않은 로컬 증거가 있다.

## 6. 독립 코드 검토와 QA

1. 작업 영역마다 구현에 참여하지 않은 읽기 전용 서브에이전트에게 diff와 설계·수용 기준 및 각 슬롯의 `focus`·질문을 전달한다. light/balanced는 한 명이 전체를 검토하고 full은 세 명이 설계 일치·회귀, 정확성·보안, 테스트·유지보수를 나눈다.
2. 선택된 검토자들이 결함과 근거를 독립적으로 검토해 원본 결과를 남긴다. 발견한 결함을 수정하면 현재 코드에 대해 프로필에 필요한 모든 코드 검토와 관련 테스트를 다시 수행한다.
3. 프로필별 코드 검토가 모두 CLEAR일 때 구현에 참여하지 않은 QA 담당자가 실제 시나리오를 수행한다. light/balanced는 담당자 한 명이 전체를 수행하고 full은 서로 다른 세 명이 정상 흐름, 경계·오류·권한, 회귀·운영 환경을 나눈다. 각자 맡은 계획 시나리오를 실제 수행하고 원본 결과를 남긴다. 프론트엔드를 작업했으면 `frontend-qa.md`에 화면·상태·입력·오류·접근성의 통합 결과를 기록한다. 백엔드를 작업했으면 `backend-qa.md`에 API·도메인·데이터·권한·오류의 통합 결과를 기록한다.
4. 양쪽이 관련되면 balanced는 통합 QA 한 명이, full은 서로 다른 세 명이 연동 QA를 진행하고 `integration-qa.md`에 API 계약과 프론트엔드·백엔드 연결 흐름의 통합 결과를 기록한다.
5. 각 계획 시나리오에 실행 환경·입력·기대 결과·실제 결과·실행 시각·통과/실패/미검증·로컬 증거 파일을 남긴다. 실패나 미실행은 재현 절차·영향도·원인·조치 근거를 기록하고 같은 시나리오를 새 증거로 재실행한다. 브라우저·실기기가 없으면 미검증으로 기록하며 PASS로 대체하지 않는다. 증거 파일은 시도마다 고유해야 하고 이전 시도를 덮어쓰지 않는다.
6. 발견한 구현 문제를 재현·수정·재검증한다. 코드 상태가 바뀌면 선택 프로필의 코드 검토 및 관련 QA를 다시 수행한다. 필요한 인원을 확보하지 못하거나 QA가 실패하면 완료로 표시하지 않는다.

완료 기준: 관련 영역마다 선택한 인원 수에 맞는 코드 검토와 QA 원본 및 통합 리포트가 있고, 선언된 수용 기준에 연결된 모든 계획 시나리오의 최신 결과가 PASS다. 연동 결과와 발견 사항의 처리 상태가 명확하다.

## 7. Markdown 리포트

`final-report.md`에 기준 문서와 범위, 실제 작업한 영역의 승인된 설계 결정, 변경 사항, 테스트 명령과 결과, 코드 검토 및 QA 요약, 해당하는 경우의 연동 QA 결과, 발견 문제와 조치, 남은 위험, 수용 기준별 통과·실패·미검증 상태를 기록한다. 작성한 설계와 QA 리포트의 로컬 경로를 연결한다. 모든 문서를 대상 Git 저장소 밖의 `~/Documents/docs/` 작업별 실행 폴더에 저장한 뒤 링크를 제공한다.

보고 전에 하네스의 `final` 게이트를 실행한다. 실패하면 빠진 증거를 실제 수행 결과로 채우거나 미검증 사유와 미완료 상태를 명시한다. 선택 검사의 미실행은 사유와 영향을 보고할 수 있지만, 필수 검사나 적용 수용 기준의 미실행·실패를 완료로 표시하지 않는다.
